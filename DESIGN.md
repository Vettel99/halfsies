# Design note: recording UPI payments so none is counted twice or lost

**Core idea:** a payment row is created *before* the user leaves for their UPI app, keyed by an ID we generate. Every signal about that payment (webhook, status poll, reconciliation report) is just an update to that one row, guarded by a state machine. A settlement only affects balances when the row reaches `SUCCEEDED`, and it can only get there once.

## 1. Data stored per payment

| Field | Why |
|---|---|
| `payment_id` (our UUID, primary key) | Sent to the partner as the merchant order/reference ID, so every webhook points back to exactly one row. |
| `client_request_id` (unique) | Generated by the app when the user taps Pay. A retry of the tap (double tap, flaky network) returns the existing row instead of creating a second payment. |
| `household_id`, `from_member`, `to_member`, `amount_paise` (integer) | What the payment is for. Fixed at creation; never changed by webhooks. |
| `status`, `status_updated_at`, `created_at` | Current state (below). |
| `partner_txn_id` (unique, nullable), `upi_rrn` | The partner's and the bank's references, filled on the first result. Unique so one bank transaction can't settle two rows. |
| `last_checked_at`, `check_attempts` | For the reconciliation job. |
| `payment_events` table (append-only): `payment_id`, `source` (webhook/poll/report), `partner_event_id` (unique), raw payload, `received_at` | Audit trail; a duplicate webhook hits the unique key and is a no-op. |

The webhook's amount is checked against `amount_paise`; a mismatch is flagged for a human, not applied. Webhook signatures are verified before anything is read.

## 2. States

```
                 user taps Pay
                      │
                  CREATED ──(user never opens UPI app, 30 min)──► EXPIRED
                      │ redirected to UPI app
                      ▼
                  PENDING ──────────────► FAILED   (terminal)
                      │
                      ▼
                 SUCCEEDED (terminal) ── writes the settlement row
```

Transitions are a single conditional update, e.g.
`UPDATE payments SET status='SUCCEEDED', ... WHERE payment_id=? AND status IN ('CREATED','PENDING')`
inside the same DB transaction that inserts the settlement (`settlements.payment_id` is UNIQUE). If 0 rows change, the payment was already final, so we return `200 OK` to the partner and do nothing. That makes the duplicate webhook harmless, and a late webhook (10 minutes after a poll already succeeded it) is also a no-op. Terminal states never change automatically; if the partner later says a `FAILED` payment succeeded (or vice versa), it goes to an ops queue because money may need refunding.

`EXPIRED` is only used when we have confirmation from the partner that no transaction exists; we never expire a payment purely on a timer, because a late success would then be "lost".

## 3. What the user sees while the result is unknown

- On returning from the UPI app: **"Payment processing: we'll update you when your bank confirms."** The suggested payment shows as *pending* and the **Pay button for that debt is disabled**, which stops the most common cause of real double payments: the user paying again because they weren't sure.
- Balances shown are confirmed balances only, plus a "₹266.66 pending to Asha" label, so nobody's balance moves on unconfirmed money.
- The app polls our server (not the partner) for the status; when it becomes final, both payer and payee get a push notification.
- If it's still pending after ~15 min: "This is taking longer than usual. Don't pay again; if money left your account it will be confirmed or refunded automatically by your bank."

## 4. Catching payments whose webhook never arrived

1. **Status poll job:** every minute, find `PENDING` / `CREATED` rows older than 2 minutes and call the partner's *transaction status API* with `payment_id`. Its answer goes through the exact same transition code as a webhook, so polling and webhooks can't double-count each other. Back off (2, 5, 15, 60 min…) using `check_attempts`.
2. **Daily reconciliation:** download the partner's settlement report and match it line by line on `payment_id` / `partner_txn_id`. Anything in the report but not `SUCCEEDED` in our DB gets succeeded through the same path; anything we think succeeded but the report lacks is flagged. This also checks our fee revenue.
3. **Alerts:** page someone if any payment is still non-final after 24h or if the reconciliation mismatch count is non-zero.

## Assumptions

- The partner accepts our own reference ID, has a status-check API and a daily report (standard for Indian UPI aggregators).
- Cash settlements (the existing `POST /settlements`) skip this flow and are recorded directly. They already take an `Idempotency-Key` header, the same idea as `client_request_id` above, so a retried request doesn't record the same cash payment twice.
